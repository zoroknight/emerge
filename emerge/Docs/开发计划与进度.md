## 1. 这份表怎么用

本文件管理“什么时候做、做到什么程度、证据在哪里”。[完整项目方案](../../参考资料/共生体-完整项目方案.md) 管理玩法与范围，[环境配置记录](环境配置记录.md) 管理工具链实测结果。

Day 1 是实际开始原型开发的第一天。赛事开始、截止时间和每日可用工时尚未提供，因此暂不填写具体日期；准备工作记为 Day 0，不代表赛事时间可以额外延长。确认赛事时间后，应把准备工作已经占用的时间计入剩余预算，再调整本表。

状态统一使用：**未开始 / 进行中 / 待验收 / 已完成 / 阻塞 / 延期**。写完代码但没有通过验收，只能标记待验收。延期任务不计入已完成。

后续每次完成一项任务，同步更新：任务状态、验证证据、当前下一项和工作日志。不要只按天数宣称完成度，也不要用任务数量推算虚假的总体百分比。

## 3. 范围与完成原则

**P0 必须交付：**可编辑身体、自由连接、四通道驱动、推力和转矩、主动摄食与能量供给、基础温度和损伤、三种经对照验证的结构效果、三段可通关地图、最低教学、失败重开、关键音画反馈与可运行包。

**P1 有条件加入：**真实收缩、感知信息、传导远端优势、五区域细化、分组封装、更多 NPC、更自然的融合膜。

**P2 暂不排入：**存储多套身体、复杂膜着色、幼体结局动画等。首版不做自主反射、周期信号、完整进化、真实流体、Boss 和程序生成地图。

地图先按安全区 → 挑战区 → 热泉圣所交付。完整五区域是扩展目标。P1 不能阻碍 P0 验收；到了排期节点，仍不成立的可选机制直接延期。

每个任务的完成要求：Unity 编译通过、验收行为可重复、留有最小验证记录、更新本表。记录可以是日志、测量表、截图或试玩结果；不要求为每次小改动都录制视频。
